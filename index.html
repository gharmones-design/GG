LESSON 01 00–15 MIN · 15 MIN

Why GoldenGate exists

Start with the business problem. Then choose the replication technology.

Your 30-second answer

Oracle GoldenGate captures committed database changes and delivers them to another system with low latency. We use it for continuous data integration, reporting feeds, consolidation, and migrations with a short cutover. Its strength is logical replication: we can select and map data, and supported source and target systems can differ.

Why not just copy the database every night?

A full copy repeatedly moves old data and leaves the target stale between copies. Change data capture (CDC) moves ongoing inserts, updates, and deletes after a baseline has been loaded. A retailer can feed new orders to analytics continuously; a bank can consolidate branch transactions without waiting for a nightly batch. GoldenGate introduces operational cost, extra logging, and eventual consistency, so the business must need that freshness or migration flexibility.

The business numbers to ask for

RPO
Recovery Point Objective: maximum acceptable data loss, usually expressed as time.
RTO
Recovery Time Objective: maximum acceptable time to restore the business service.
Freshness SLA
How old data may be at the consumer. Different from recovery objectives.
Cutover window
How long writes or service may pause while changing the system of record.

Illustrative business case: a 60-minute outage at an estimated $2,000/minute means $120,000 of outage exposure. Reducing cutover to five minutes could reduce that exposure by $110,000 for that event. Compare expected benefit against licenses, infrastructure, engineering, support, and reconciliation. These are example assumptions, not a quotation or guaranteed savings.

Topologies: say the business reason

One → one: migration or reporting. One → many: distribute a common feed. Many → one: consolidate branches. Two-way / many-way: local writes with harder conflict management. A topology drawing does not prove an application can safely write everywhere.

Practice · “We only need whole-database Oracle DR. Why buy GG?”

Start by evaluating Data Guard against RPO/RTO. GG becomes relevant if there is also a requirement for selective replication, transformations, supported heterogeneous platforms, or migration flexibility. Do not choose GG solely because it is called real-time.

The path of one transaction

Keep management services separate from the actual data flow.

What is a microservice here?

A microservice is a focused service with a defined interface. GoldenGate Microservices Architecture (MA) splits administration, transport, reception and monitoring into REST-accessible services. Use a browser, Admin Client, or REST API to manage them. It does not mean every table becomes a microservice, and it does not require your application to use microservices or Kubernetes.

Example: an application updates order 42 and commits. Capture obtains the change records, Extract writes the selected committed transaction to a trail, the path transfers the data, and Replicat applies it. A rolled-back transaction is not delivered as a committed business change. If only some tables are configured, the target represents that selected scope, not necessarily the whole application transaction.

Three objects that make recovery possible

Trail
Ordered files containing captured records. They decouple capture, transport and apply. During a network outage capture may continue while trail disk remains available.
Checkpoint
A saved processing position used for correct restart. Not a backup. Depending on mode, positions live in files, tables, and database-managed state.
Parameter file
Defines credentials, trails, selection, mapping and behavior. TABLE selects source objects; MAP … TARGET defines delivery mappings.

A deployment is a configuration boundary

A deployment has configuration, runtime files, credentials and service endpoints. The installed software is separate from deployment data. Know OGG_HOME, OGG_ETC_HOME for configuration, OGG_VAR_HOME for variable runtime data, and the configured trail location. Example ports are not universal defaults.

Use secure deployments and TLS transport according to the environment. Credential aliases keep database passwords out of parameter files. GG deployment users and database users are different identities. A target-initiated path lets the target establish the connection for restrictive firewalls; data still flows source to target.

Practice · “Extract is running but nothing reaches the target.”

Follow the pipeline: Extract statistics and local trail growth; path status and connectivity; Receiver and target trail growth; then Replicat state and apply progress. RUNNING is not proof of end-to-end delivery.

PDF pp. 18–35; target-initiated paths pp. 174–180. Spend 10 minutes learning and 5 minutes redrawing the flow.

Integrated Extract, explained precisely

The database logmining server performs mining. Extract receives LCRs and produces the trail. REGISTER EXTRACT … DATABASE establishes the database-side capture relationship. Integration helps support Oracle features such as RAC, ASM and TDE. “Integrated” does not mean the external Extract process disappears.

Local mining: mining runs in the source database. Downstream mining: redo is transported to a separate Oracle mining database, reducing source mining work. Real-time downstream mining uses standby redo logs; archived-log-only downstream mining waits for archived logs. Source logging and shipping still cost resources. Running the GG executable remotely does not by itself move database mining off the source.

Integrated processes need suitable database privileges, a dedicated database connection, and enough Streams pool memory. Diagnose mining waits and memory as well as the external process. Tune parallelism only after checking CPU, memory, redo availability and workload.

Dependencies respected

The inbound server computes dependencies using target keys and constraints. Independent transactions can commit out of source order; dependent transactions must retain required order. Transaction atomicity is preserved within this supported configuration. “Parallel” does not mean arbitrary order. Index foreign-key columns as the guide requires.

DDL and certain operations, including some SQLEXEC work, use direct apply. Replicat drains prior inbound work, executes the operation directly, then resumes integrated processing. Frequent barriers can reduce throughput. Not every operation is applied in parallel inside the database.

Two answers to remember

Integrated Extract uses the source/mining logmining server. Integrated Replicat uses the target inbound server. Capture and apply modes are independent choices.

Do not use Integrated Replicat for initial load. The guide explicitly limits it to online processing.

Practice · “Why not always use Integrated Replicat?”

It is Oracle-target specific, uses database resources, and some operations serialize. The PDF recommends parallel non-integrated Replicat unless a feature dictates another mode. Check certification and benchmark the real transaction mix rather than choosing by the word “integrated.”

PDF pp. 128–133 and 184–205, especially 188–193. Spend 14 minutes learning and 6 minutes comparing modes aloud.

LESSON 04 50–85 MIN · 35 MIN

Initial load & the SCN handoff

The highest-priority lesson: explain why there is neither a gap nor an overlap.

The invariant

Correct target = consistent baseline + every required committed change after the baseline. Capture must cover all transactions needed after the boundary, including transactions that were already open. Record one boundary consistently, retain required redo and trails, and validate the result.

First resolve “start the Replicat”

There are two lanes and two Replicats. REPINIT loads baseline rows. REPPRIM applies ongoing CDC later. The PDF starts the primary Extract first, determines the SCN, starts REPINIT, runs EXTINIT, transports the files, and finally starts REPPRIM after the load completes. Starting REPINIT early lets it wait for initial-load input. It does not mean applying CDC into an incomplete baseline.

CDC lane · capture runs throughout

Source redo → EXTPRIM → aa → path → bb → REPPRIM

REPPRIM stays stopped until the baseline is complete.
Baseline lane · one-time load

Tables AS OF S → EXTINIT → cc → path → dd → REPINIT

REPINIT populates the target while source changes accumulate separately.

The p. 160 figure associates AA/BB with initial load, but the worked commands on pp. 162–167 use AA/BB for CDC and CC/DD for initial load. This course follows the worked command mapping. Trail names are arbitrary; correct producer/consumer connections matter.

SCN is not a timestamp or a trail position

SCN
Oracle System Change Number: a logical ordering point. AS OF SCN S reconstructs a consistent database view at S.
Start SCN
When a transaction began; useful for old open transactions, but different from its commit SCN.
Commit SCN / CSN
The transaction’s commit ordering value. GG uses Commit Sequence Number (CSN); for Oracle this is an SCN.
Registration SCN R
The database capture registration point recorded for primary integrated Extract.
Instantiation SCN S
The baseline boundary. In the PDF’s precise-instantiation procedure, S must be later than R.
Sequence + RBA
A trail file number and byte position. Different from a logical commit boundary.

The six steps in your PDF

  1. Create and start EXTPRIM.

    Complete logging and database preparation. Create/register integrated capture, record R from the registration output, configure the CDC trail and tables, and start capture. Confirm capture health and retain trails. Do not repeatedly register just to “get another SCN.”

  2. Establish S after old transactions drain.

    Monitor all RAC instances with GV$TRANSACTION. Wait until the oldest open transaction start SCN is greater than R. If none are open, use the current SCN. Record S and verify S > R. The goal is complete capture coverage, not waiting a fixed number of minutes.

  3. Create and start target REPINIT.

    Prepare target objects and the checkpoint table. REPINIT consumes dd and loads baseline rows. Prevent ordinary application writes in the target scope; configure triggers and constraints deliberately for the load method.

  4. Create and start source EXTINIT.

    Read selected tables at the same consistent AS OF SCN S and write cc. Retained undo must support the entire scan. Keep EXTPRIM running.

  5. Create and start both paths.

    Transfer aa → bb for CDC and cc → dd for the baseline. Paths can be prepared earlier when supported. The essential dependencies are baseline completeness and retained CDC coverage, not the exact time a path is created.

  6. Complete the load, then start REPPRIM at the correct boundary.

    Confirm EXTINIT finished and REPINIT consumed the entire baseline with no unresolved errors. Create REPPRIM on bb. Use the boundary rule for your validated load method, let CDC catch up, and reconcile before cutover. Preserve initial-load evidence until validation.

Why old open transactions matter

Suppose registration is R = 1,000. A transaction started at 950 and remains open. A snapshot at 1,050 excludes its uncommitted changes, but it may commit at 1,100. If capture cannot supply it from the required beginning, the combined baseline and CDC may miss it. The PDF’s method waits until no open transaction started at or before R before choosing S.

A transaction starting at 1,080 and committing at 1,150 crosses a snapshot at S = 1,100. The snapshot excludes it, so CDC must include it. Commit position, not transaction start time, determines whether it belongs after the snapshot.

Cutover is a business event

  1. Fence source writes and drain transactions under the agreed plan.
  2. Record the final boundary; prove capture, transport and apply reached it.
  3. Reconcile critical data and business totals at comparable points. Zero lag alone is insufficient.
  4. Switch application connections, test business operations, then allow writes on the new system of record.
  5. Keep a rollback window. After target-only writes, switching back needs validated reverse synchronization or recovery.
Practice · “Take the SCN, export, then start Extract?”

Not as a casual live-migration sequence. Changes during export can fall into a capture gap. Start and validate capture first, select a safe boundary with a supported method, retain changes, load the baseline, then apply the required commits.

Practice · “The load takes four hours. What storage is required?”

Retained undo must reconstruct the snapshot throughout the scan. Trails need capacity for loading, interruptions and catch-up. Archive retention must cover recovery and long transactions. Measure real rates and add headroom; UNDO_RETENTION alone does not prove sufficient space.

LESSON 05 85–100 MIN · 15 MIN

Operate without losing correctness

Locate the fault before choosing the fix.

Prerequisites you cannot skip

  • Logging: ARCHIVELOG, database supplemental logging, table/schema logging and appropriate FORCE LOGGING. Required keys and scheduling columns must reach the trail.
  • Keys: reliable unique row identity and useful target indexes. Otherwise matching can be costly or ambiguous.
  • Compatibility: supported versions, objects, data types, DDL, character sets and workload features. Oracle-to-Oracle does not mean every object is supported.
  • Target behavior: coordinate triggers, constraints, sequences, jobs, DDL and application writes. Do not execute the same business side effect twice.
  • Capacity/security: redo retention, snapshot undo, trails, memory, credentials, TLS, privileges and alert ownership.

Why supplemental logging? Ordinary redo may lack unchanged key or scheduling values needed to identify a target row and calculate dependencies. ADD TRANDATA is table-level; ADD SCHEMATRANDATA covers current and future tables in a schema. Extra logging increases redo volume.

Two capacity calculations

Trail capacity: measured trail rate × maximum unconsumed time + margin. At 20 GB/hour for six hours, the base is 120 GB; 50% headroom gives 180 GB at that location. Size source and target separately and allow for load files. The PDF’s 40%-of-redo estimate is a starting heuristic, not a universal ratio.

Catch-up time: backlog ÷ (apply rate − arrival rate), with compatible units and stable rates. A 60-million-row backlog at 30,000 rows/s apply and 20,000 rows/s arrival takes 6,000 seconds, or 100 minutes. If apply is no faster than arrival, it never catches up under those conditions.

Active-active starts with a business policy

Two sites may update the same customer before seeing each other’s change. Prefer partitioned write ownership where possible. Define globally unique keys, supported conflict detection/resolution and an audit trail. “Latest timestamp wins” can discard legitimate changes; it is not a universal rule for financial data.

Loop suppression is different from conflict resolution. The Oracle example tags Replicat-applied transactions with DBOPTIONS SETTAG and excludes them using TRANLOGOPTIONS EXCLUDETAG. This prevents recapture loops; it does not decide which competing application update wins. Non-Oracle mechanisms differ.

HANDLECOLLISIONS is not a repair plan. It can hide overlap symptoms and divergence. A correctly bounded precise Oracle instantiation should not need it as a blanket workaround. Skipping error transactions can discard legitimate business work.
Practice · “Everything is RUNNING. Do the systems match?”

Check recent end-to-end heartbeats, advancing positions, throughput, unresolved errors/discards and data reconciliation at a comparable boundary. Matching counts can hide different values. Include business totals and key-level checks for critical data.

LESSON 06 100–120 MIN · 20 MIN

Practice the manager’s questions

Answer with a decision, a reason, evidence, and the business consequence.

Spend 8 minutes answering any four cases aloud, 7 minutes on the quiz, and 5 minutes drawing the initial-load sequence from memory. The remaining cases are optional revision. These are practice scenarios inferred from the guide and your request, not predictions of the exact evaluation.

A strong answer structure

“The requirement is ___. I would choose ___ because ___. Before proceeding I would verify ___. The main business risk is ___, and I would prove success using ___.”

CASE 01

Migration with five minutes of outage

A 2 TB Oracle database must move to a supported target platform. Business permits five minutes of write outage.

Reveal a strong answer

Start capture before a consistent baseline. Prove the SCN boundary and undo/trail capacity. Catch up before cutover; fence writes, drain transactions, reach the final boundary, reconcile, switch and smoke-test. Rehearse the full sequence against measured throughput. Define rollback after target writes.

Weak answer: promise zero downtime because GG is real-time, or start capture after the copy.

CASE 02

A transaction older than registration

R = 1,000. The oldest open transaction started at 900. Current SCN is 1,500. Can you immediately use 1,500 in the PDF’s recipe?

Reveal a strong answer

Not under that recipe. Wait until the oldest open start is later than R, or use a separately validated method that covers the old transaction. A high current SCN does not prove complete capture coverage. Then record S and use it consistently.

Weak answer: check CURRENT_SCN and ignore the long transaction.

CASE 03

A duplicate after the baseline

The baseline includes an insert committed at S. Primary apply starts ATCSN S and encounters the same key.

Reveal a strong answer

ATCSN includes S, so investigate overlap. Compare the snapshot and exact trail transaction, confirm the method, repair affected state and use its validated boundary. For a baseline containing every commit through S, AFTERCSN expresses the exclusive boundary.

Weak answer: enable HANDLECOLLISIONS or ignore every duplicate.

CASE 04

A two-hour network outage

Extract is healthy, local trails grow, and the target stops advancing.

Reveal a strong answer

Inspect the path/Receiver connection, trust, credentials and disks. Quantify buffer time, communicate freshness impact, preserve trails, restore transport and measure catch-up. Do not restart everything or delete unconsumed trails.

Weak answer: declare no risk because Extract is running.

CASE 05

Disaster recovery or integration?

The manager wants zero data loss on failure of an entire Oracle database. No transformations or non-Oracle targets are required.

Reveal a strong answer

Evaluate Data Guard protection modes, transport constraints and tested failover against RPO/RTO. GG may complement an integration requirement. Do not promise that asynchronous GG guarantees zero loss in every failure.

Weak answer: treat “real-time” as a data-loss guarantee.

CASE 06

Two branches change one balance

Both branches update the same account during a network partition.

Reveal a strong answer

Ask who owns writes and what business behavior is allowed. Prefer preventing concurrent ownership for that record, or use a validated business-specific conflict policy with auditing. Unique keys and loop suppression are separate requirements. GG eventual consistency is not a distributed account lock.

Weak answer: claim EXCLUDETAG resolves conflicting updates or blindly use last-writer-wins.

CASE 07

More appliers, still more lag

Target CPU is busy, parent/child tables lack useful indexes, and DDL is frequent.

Reveal a strong answer

Measure waits and dependencies. Index required key/foreign-key paths; review barriers and transaction sizes. Tune parallelism with evidence. More appliers can increase contention without increasing useful throughput.

Weak answer: keep adding threads without identifying the bottleneck.

CASE 08

Same row count, different finance total

Both databases have one million rows and low reported lag, but a business total differs.

Reveal a strong answer

Compare at the same logical boundary and scope. Inspect values, mappings, filters, discards, target writes and load boundaries. Counts and low lag do not prove consistency. Reconcile and repair before cutover approval.

Weak answer: sign off because counts match.

The essentials, on one page

Remember first

  • GG moves selected committed changes.
  • Data Guard protects an Oracle database; GG offers logical flexibility.
  • Capture and apply modes are independent.
  • Start capture before the live baseline.
  • One consistent S, complete coverage, no gap or overlap.
  • REPINIT loads; REPPRIM synchronizes later.
  • Integrated Replicat is not for initial load.
  • RUNNING and low lag do not prove equal data.

  • RPO, RTO, freshness and cutover window?

  • Validation, cutover owner and rollback?
